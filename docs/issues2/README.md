# 任务池：毕设裁减（thesis-trim）

> **来源**：[毕设裁减方案 v0.8](task-thesis-trim-plan.md)，基线 `d6e04aa`。拆分前先做了一次代码审核，结论见[审核报告](review-thesis-trim-plan-v0.7.md)。
> **拆分原则**：每个 issue 是一个可以独立验收、单独提交、单独 revert 的工作包。粒度按"能不能单独交付"来定：大专题拆成几个包，小专题一个包。每个 issue 都写明依赖、预计改动路径和需要用户拍板的决策，并尽量避免两个会话同时改同一批文件。
> **与方案的关系**：方案定范围、裁决和约束，issue 定怎么分包、按什么顺序交付。两者冲突时，以方案 §2 的裁决台账为准，并回到方案登记变更。
> **派发方式**：由用户在新的 agent 会话里指定 issue 编号来领取。

## 一、领取与交付流程（所有 issue 通用）

1. **确认可以开工**：issue 状态为"待领取"，依赖的 issue 已经完成，"需用户决策"一栏里的决策都已拍板。若要与正在进行的其他 issue 同时开工，先查第三节的并行矩阵，只开 ✅ 的组合。
2. **准备环境**：新 worktree 缺少依赖，先在根目录、`web/`、`container/agent-runner/` 各执行一次 `npm ci`。
3. **领取**：在任务分支里把 issue 状态改为"进行中"，填上领取人（会话名或分支名），同时更新本文件索引表里对应的那一行，随立项提交一起提交。
4. **按 [`docs/workflow.md`](../workflow.md) 执行**：
   - 需求采访：issue 里标注"需用户决策"的项，**先列出方案请用户拍板，不要自行决定**；
   - 立项：编写 `docs/<任务名>-plan.md`，重置 `.gatescope.json`（`base` 填开工前的 HEAD，`allow` 列出 issue 的预计改动路径）；
   - 实现：TDD，先写 Red 用例；
   - 验证：依次执行 `npm run verify`（六步门禁）和 `node scripts/check-scope.mjs`。
5. **提交**：提交信息首行格式为 `type: 范围 - 摘要`，由 commit-msg 钩子校验。禁止 `--no-verify`。合入 main 由用户决定，代理不推送。
6. **交付**：三处状态必须同步改为"已完成"，随交付提交一起提交，缺一处不算交付：
   - issue 文件元信息表里的"状态"；
   - **本文件第二节索引表里对应行的"状态"列**；
   - 方案 §2 裁决台账里该专题的状态（一个专题的全部 issue 都完成后才改，写明提交号）。

   同时在 issue 末尾的"交付记录"里写明提交号、验证结果，以及与 issue 描述的偏差。

7. **发现范围外的新问题**：不扩大本 issue 的范围。在本目录新建 issue（编号顺延），或者在交付记录里登记。

### 所有 issue 都要遵守的约束

- **方案 §3 的八条裁剪原则**，尤其是：表结构只在 THESIS-14 里动；`data/` 是敏感区，代理不读写；删除前用 `git grep -w` 交叉核实调用方，范围包含 `tests/` 和 `docs/`。
- **审查口径**沿用 [R2 任务池](../issues/README.md)：掉线逻辑先请用户决定；有专门测试或注释写明设计动机的"意图信号"默认保留。
- **前端一并裁净**（方案 §11）：每个包删掉功能后，前端不留孤儿文件、死导出和无人使用的依赖。方案 §11.4 的检查项是每个前端相关包的验收条件之一。
- **文档随包同步**：每个包同步自己涉及的 `docs/API.md`、`docs/ACL-MATRIX.md` 行，并跑 `npm run docs:check`。"多用户改为个人"的产品定位改写单独放在 THESIS-13。
- **锚点**：issue 里的 `文件:行号` 都是 `d6e04aa` 的行号。执行时以符号名为准，用 grep 重新定位。
- 修改共享类型后执行 `make sync-types`；修改数据库要在同一提交里更新 `tests/db-upgrade-safety.test.ts` 的版本号钉。

## 三、并行关系与执行顺序

### 3.1 判定口径

| 标记 | 含义                                                                                                                                          |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅   | **可以并行**：两个 issue 不共享源码与测试文件，最多共享文档的不同小节                                                                         |
| ⚠️   | **可以并行，但合入时会有冲突**：共享源码、测试或文档，改的是不同区域。尽量错开；确需同时进行时，后合入的一方先 rebase 最新 main，手工解决冲突 |
| ❌   | **不可并行**：有依赖关系，或改同一文件的同一或相邻区域                                                                                        |

判定依据是各 issue 的"预计改动路径"和锚点所在区域。执行中如果改动范围超出预计改动路径，要按实际范围重新对照本节。

**簿记冲突（任意两个并行 issue 都会遇到）**：每个 issue 立项时都会重置仓库根的 `.gatescope.json`，也都会改本文件索引表里自己那一行，所以并行分支合入 main 时这两处一定冲突。处理方式：`.gatescope.json` 取后合入那个 issue 的版本；索引表两边的状态改动都保留。
