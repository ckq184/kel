## 0. 审查口径

### 0.1 判定规则（用户指定）

1. 不只查“谁调用”，还查“产出有没有人消费”。对每个候选都追数据流：返回值或副作用流向哪个字段、文件或事件，下游现在还有没有消费者。
2. **有消费者、没有生产者 → 登记为“掉线逻辑”，不删。**
3. **有专门测试，或注释写明了设计动机 → 视为“意图信号”，默认保留并登记，交你判断。**
4. 不过早下结论，靠交叉认证：同一结论尽量由两条独立路径得出，主线程对高影响结论逐行复核。

### 0.2 分类标签

| 标签        | 含义                                                                                                | 本报告的处理建议                                 |
| ----------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **BROKEN**  | 断链：上游生产者还在（UI 能改、宿主会注入），中游或终端的消费者没了，用户可见的设置或提示**不生效** | 按功能缺口处理，与 DROPPED 同级，**不删**        |
| **DROPPED** | 掉线逻辑：消费端还在，生产端没了                                                                    | **不删**；先决定是补生产者，还是连消费端一起下线 |
| **INTENT**  | 意图信号：有专门测试或设计注释                                                                      | 保留登记，交你判断                               |
| **DEAD**    | 确定死代码：没有调用者，或产出无人消费，且没有意图信号                                              | 可删（需你批准）                                 |
| **COMPAT**  | 兼容层残留：legacy 路由、双写字段、为旧客户端保留的分支                                             | 判断兼容期是否结束                               |
| **DUP**     | 重复实现                                                                                            | 可合并                                           |
| **BLOAT**   | 臃肿：多余的 export、无效请求、超大文件                                                             | 低优先级                                         |

## 2. 总览：断链有两个源头

| 源头                                                                                              | 表现                                                                                                                                                     | 量级                                            |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **A. Claude SDK runner 换成 Pi runner**（64d6d7b 删除旧 runner）                                  | 宿主、飞书卡片、Web 仍按 Claude SDK 的事件契约和设置工作，Pi runner 不产出这些事件，也不读这些设置。旧 runner 被删时，**生产端随之消失，消费端全部留下** | 本报告中**最大、最重要**的一类，P0 几乎都在这里 |

**一句话结论**：仓库里纯粹的死代码不多（第一轮已清掉大头）。真正值得关注的是 **A 类断链**：至少 6 项 Web 设置在 Pi 下不生效，Web 流式输出与飞书卡片正文可能被静默丢弃或回滚，子代理和工具状态显示失真。这些都应该**先确认、再决定补哪一侧**，不能当死代码删。

### 14.5 两份报告的分工建议

- **处理顺序以本报告 §13 为准**：B 报告建议的批 1“A 类快赢”只涉及纯删除，没有覆盖 P0 断链。如果先删再修，删除时很可能顺手删掉 P0 修复要用的消费端（例如 hook、raw_sdk_event 簇，或 `extractSkillName`）。
