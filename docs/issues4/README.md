# 任务池：个人版深度裁减与巨型文件瘦身（personal-slim）

> **来源**：[personal-slim 方案 v1.1](task-personal-slim-plan.md)，基线 main `607d1b6`。方案定范围与裁决（§2 台账 P1 至 P10），本池定怎么分包、按什么顺序交付；两者冲突时以方案为准。
> **v1.1 要点**：系统只保留管理员一个角色；多用户代码（其他角色、数据归属、按用户的存储与运行时结构）全部裁减；本机账号均为测试账号，不写数据搬迁。新增 THESIS-34 至 37。
> **前置**：排在 [issues3](../issues3/README.md)（THESIS-16 至 18，已全部完成）之后。
> **派发方式**：由用户在新的 agent 会话里指定 issue 编号来领取。

## 一、领取与交付流程

沿用 [thesis-trim 任务池第一节](../issues2/README.md#一领取与交付流程所有-issue-通用)的流程与"所有 issue 都要遵守的约束"，另加：

1. **硬约束**：方案 §3 的四条新增约束（迁移链不动、IM 侧访问控制不动、归属列保留不读、非多用户的分层保留）。
2. **只读查看数据库**：经用户授权，领取的会话可以只读查看本机 `data/db/messages.db` 做验证（服务停止时用 `?immutable=1` 打开）；不写 `data/`，不读密钥与消息内容。
3. **交付时同步三处状态**：issue 文件元信息表的"状态"、本文件第二节索引表对应行、方案 §2 台账的"执行包"一栏（该裁决的全部包完成后写提交号）。
4. **锚点基准**：`文件:行号` 均为 `607d1b6`。前面的包合入后行号会漂移，以符号名 grep 重新定位。
5. **拆分包（THESIS-28 至 33）只搬代码、不改行为**：每个提交前后 `npm run verify` 全绿；读源码文本的契约测试随文件搬迁改读新路径，不得删除断言来"让测试通过"。
